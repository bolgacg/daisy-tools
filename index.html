DAISY, measured

DAISY, the Danish Foundation Models benchmark on the Danish Culture Canon, asks what a language model knows about Danish culture. This page measures the whole apparatus around that question. The published numbers are reproduced from the released files; the common way of running Mimir turns out to read its prompt backwards and is fixed in 35 lines; the benchmark's own noise is counted; and the same models are then given one Wikipedia lookup and the choice of when to use it. Mimir moves from to with the lookup, and no model tested here knows when to look.

Contents

    Terms

    Five small language models are measured on DAISY under identical conditions: answering from memory, answering after one Wikipedia lookup, and choosing whether to look. DAISY has 592 public questions; the published Mimir score was computed on the same 592. Two search engines appear through the page: Wikipedia's own search box, which requires every word of a query to match, and a standard ranked index (BM25) built here over the full Danish Wikipedia dump of 1 November 2023. The terms below carry the analysis. Any dotted-underlined term anywhere on this page shows its definition on hover, and the small i markers explain whatever they sit next to.

    From memory
    The model answers with nothing but the official Danish prompt, exactly as in the DAISY paper.
    One lookup
    The question, as written, is sent to a search over Danish Wikipedia, and the introductions of the top three pages are placed above the prompt. No model writes a query.
    Exact match
    The official score: the normalised answer equals the reference answer.
    Contains-gold
    A softer score reported beside it: the reference answer appears somewhere inside the model's answer. Used where a published comparison uses it.
    Answer recall
    How often the reference answer is inside the fetched text. The ceiling of a lookup: no reader can exceed it.
    Reading fidelity
    Exact match restricted to the questions where the answer was in the fetched text. Separates "could not find it" from "could not read it".
    Decision
    Whether a model that is allowed to search chooses to search, and whether that choice tracks what its memory can actually deliver.
    Prefix attention
    Mimir reads the prompt with every token attending to every other token; the common llama.cpp port reads left to right only. A 35-line fix built for this study restores the trained behaviour.

    Broken and fixed

    Three findings from the reproduction work: a port that reads backwards, a prompt that exists in two versions, and the benchmark's own noise, counted.

    The community port, fixed

    The change and its checker are in tools/prefix-run, and the fix is open as a pull request to the port's author.

    Two copies of the prompt

    The DAISY prompt exists twice in public code, and the two copies differ by one blank line. The evaluation script in the SDU-Daisy repository starts the prompt with a newline and puts two blank lines before the question; the copy in the dfm-evals library puts one. The tokenizer turns the blank lines into a single token, a different one in each copy, so every prompt differs by exactly one token. On 60 questions with the same model and greedy decoding, that one token rewrote 13 answers while the exact-match score did not move. Two answers the token changed: the composer of Drømmeland went from Carl Nielsen to Jens Christian Dahl, the author of Enten-Eller from Jens Peter Jacobsen to Herman Bang, both wrong before and after. The conclusion for anyone comparing runs: a 592-question exact-match benchmark cannot see a change that rewrites a fifth of the answers, and a byte-level diff of the prompt can. The harness behind this page uses the script's copy for every row; the check in the dfm-evals framework uses the library's copy, and the two land within half a point on the same model (66.0 against 65.7).

    Why the score cannot yet test the decision

    When memory is right on 3 to 8% of questions, "always search" is close to the best policy, so a high rate of searching when wrong is not judgement. What can be measured now is the bluff: a model claiming to know when it does not.

    Finding is solved by the index, reading by the model. Knowing when to look is solved by nothing on this page, and that is the training problem the position is about.

    Placement among English systems

    English open-domain QA systems trained for the task with far larger models score 44 to 64 exact match on Natural Questions (RAG, Fusion-in-Decoder, Atlas). Untrained 1B and 4B models at here sit in that band; the tasks differ, so this is a placement, not a comparison.

    Adaptive retrieval (Mallen et al., arXiv 2212.10511) pays only when memory is worth something; here memory is right on 1 to 8% of questions, so always retrieving is the best policy, although token log-probabilities predict correctness well (AUROC 0.83 to 0.91). No published Danish retrieval-augmented QA number was found in the literature sweep; the tables above are the first.

    Questions and answers

    Questions asked by readers of earlier drafts, answered in order. A new reader is likely to have the same ones.

    What does reading the prompt one way versus both ways mean?

    A model normally reads a prompt one token at a time, and each token can only use the tokens before it, because that is how it writes. Mimir was trained so that, while reading the question, every token may also use the tokens after it; only the answer is written left to right. The community port supports the first mode only. Same weights: read the wrong way, read the right way.

    Tools built

    Everything on this page runs from code in the repository. Each tool exists because a measurement needed it.

    • The harness (daisy_tools/runner.py, ~400 lines): runs every condition on this page against any OpenAI-compatible server and logs prompt, answer, query, fetched pages, tokens and seconds for every question, resumable by question id. Exists so every number is a logged record, not a printout.
    • The offline index (scripts/build_localwiki.py, 60 lines): the full Danish Wikipedia dump of 1 November 2023 in a SQLite full-text index with BM25 ranking, 0.9 GB, built in about twenty minutes. Exists because the live search box requires every word to match and buries the lookup's real ceiling.
    • The prefix-attention fix (tools/prefix-run/, 35 changed lines in llama.cpp plus a standalone driver): makes the community port read the prompt the way Mimir was trained. Validated against the official implementation on all 592 questions, three ways. Exists because the port silently lost a third of Mimir's score.
    • The checker (tools/prefix-run/compare_server.py): asks a running server the same questions as a reference run and reports word-identical answers, not just equal scores. Exists because two runs can share a score and disagree on a fifth of their answers.
    • The task in the dfm-evals format (dfm_evals_task/): DAISY with one lookup, and with the lookup as a native tool, as Inspect AI tasks that keep the official prompt, decoding and scorer; run.sh runs everything in one command. Exists so the group can reproduce the headline number inside the framework it already uses.
    • The official-path runner (scripts/mimir_official.py): Mimir through the transformers implementation with prefix attention, switchable between the three public prompt variants and precisions. The reference every other Mimir number is checked against.
    • The page builder (scripts/build_page_data.py): recomputes every number on this page from the logged runs and the released files; nothing is typed in. The headless walk (verification/walk.js) fails the build on console errors, layout overflow, overlapping chart text or unexplained empty cells.

    Model card

    ModelParametersWeights usedEM from memoryEM, one lookup

    Nothing was trained. Four models run quantised through llama.cpp; Mimir runs in the official implementation at half precision with prefix attention. Greedy decoding, at most 64 new tokens, the official prompt, each model's chat template, three introductions of at most 900 characters, the official scorer unmodified, one GeForce GTX 1060 with six gigabytes.

    Is it any good? As a measurement, yes: it reproduces the published ranking on the released files and the published Mimir number on the official code path. As a system, a one-billion-parameter Danish model with one lookup answers two thirds of this benchmark exactly.

    Limits

    • 592 questions: the 95% interval on a score near 65 is about plus or minus 4 points.
    • The questions were written from Wikipedia pages, so the score says how well pages are found and read, not how the models do on facts outside Wikipedia.
    • One index, one snapshot, one query rule, three introductions of 900 characters, one run at temperature zero.
    • The decision table cannot separate judgement from "always search" at this level of memory.
    • No fine-tuning. The training route named in the call, reinforcement learning on tool calls, is the natural next step.

    Run it yourself

    The lookup is a task in the dfm-evals format (Inspect AI). One command runs everything and prints the table; the Inspect viewer then shows every question, fetched text, answer and score.

    git clone https://github.com/bolgacg/daisy-tools && cd daisy-tools
bash run.sh                # index (20 min the first time), weights, server, the daisy task and the lookup task, the table
.venv-inspect/bin/inspect view --log-dir results/inspect
