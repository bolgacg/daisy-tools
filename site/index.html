What one Wikipedia lookup does to DAISY, and what it cannot do

DAISY, the group's quiz on the Danish Culture Canon, measures what a model remembers. Give the same models one lookup in Danish Wikipedia and the quiz measures three separate skills: finding the page, reading it, and knowing when to look. The group's own one-billion-parameter Mimir goes from to , level with a model four times its size, and no model here knows when to look.

Chapters

    Five things to know

    1. DAISY is the group's quiz of short factual questions about the Danish Culture Canon. The 592 public questions are used here; the group's own Mimir score was computed on the same 592.
    2. From memory means the model answers with nothing but the group's Danish prompt, exactly as in their paper.
    3. One lookup means the question, as written, is sent to a search over Danish Wikipedia, and the introductions of the top three pages are placed above the prompt. No model writes a query.
    4. Two search engines are compared: Wikipedia's own search box, which needs every word to match, and a standard ranked index (BM25) built here over the full Danish Wikipedia dump of 1 November 2023.
    5. Scores are the group's: exact match, the normalised answer equals the reference. Contains-gold is shown beside it: the reference appears inside the answer.
    Answer recall
    How often the reference answer is inside the fetched text. The ceiling of a lookup.
    Reading fidelity
    Exact match on the questions where the answer was in the fetched text. Separates "could not find it" from "could not read it".
    Oracle query
    The benchmark's hidden subject field used as the search term. The best possible query; a model never sees it.
    Decision
    Whether a model told it may search does search, compared with whether its memory was right.
    Prefix attention
    Mimir reads the prompt with every token seeing every other token. The common laptop port reads left to right only.

    Why the score cannot yet test the decision

    When memory is right on 3 to 8 percent of questions, "always search" is close to the best policy, so a high rate of searching when wrong is not judgement. What can be measured now is the bluff: a model claiming to know when it does not.

    Questions asked along the way

    The questions the author was asked while building this, in order. A reader will have the same ones.

    What do you mean by reading the prompt one way versus both ways?

    A model normally reads a prompt one token at a time and each token can only use the tokens before it, because that is how it writes. Mimir was trained so that, while reading the question, every token may also use the tokens after it; only the answer is written left to right. The laptop port supports the first mode only. Same weights: read the wrong way, read the right way.

    Two copies of the prompt

    The group's prompt exists twice in their public code, and the two copies differ by one blank line. The evaluation script in the SDU-Daisy repository starts the prompt with a newline and puts two blank lines before the question; the copy in their evaluation library puts one. The tokenizer turns the blank lines into a single token, a different one in each copy, so every prompt differs by exactly one token. On 60 questions with the same model and greedy decoding, that one token rewrote 13 answers while the exact-match score did not move. Two answers the tokens changed: the composer of Drømmeland went from Carl Nielsen to Jens Christian Dahl, the author of Enten-Eller from Jens Peter Jacobsen to Herman Bang, both wrong before and after. The lesson for anyone comparing runs: a 592-question exact-match quiz cannot see a change that rewrites a fifth of the answers, and a diff of the prompt bytes can. This page's harness uses the script's copy for every row; the check in their own framework uses the library's copy, and the two land within half a point on the same model (66.0 against 65.7).

    Tools built

    Everything on this page runs from code in the repository. What each piece is, in one line.

    • The harness (daisy_tools/runner.py): every condition on this page, against any OpenAI-compatible server, logging prompt, answer, query, fetched pages, tokens and seconds per question, resumable by question id.
    • The offline index (scripts/build_localwiki.py): the full Danish Wikipedia dump of 1 November 2023 in a SQLite full-text index with BM25 ranking, 0.9 GB, built in about twenty minutes.
    • The task in their format (dfm_evals_task/): DAISY with one lookup and DAISY with the lookup as a tool, as Inspect AI tasks that keep their prompt, decoding and scorer; run.sh runs everything in one command.
    • The official-path runner (scripts/mimir_official.py): Mimir through the transformers implementation with the prompt read in both directions, the reference every other Mimir number is checked against.
    • The prefix-mode driver and patch (tools/prefix-run/): the community llama.cpp port made to read the prompt the way Mimir was trained, first through the public API without touching llama.cpp, then as a fifteen-line change to the port itself.
    • The page builder (scripts/build_page_data.py): every number on this page is computed from the logged answers; nothing is typed in.

    Model card

    ModelParametersWeights usedEM from memoryEM, one lookup

    Nothing was trained. Four models run quantised through llama.cpp; Mimir runs in the official implementation at half precision with prefix attention. Greedy decoding, at most 64 new tokens, the group's prompt, each model's chat template, three introductions of at most 900 characters, the group's scorer unmodified, one GeForce GTX 1060 with six gigabytes.

    Is it any good? As a measurement, yes: it reproduces the group's ranking on their files and their Mimir number on their code path. As a system, a one-billion-parameter Danish model with one lookup answers two thirds of this quiz exactly.

    Limits

    • 592 questions: the 95 percent interval on a score near 65 is about plus or minus 4 points.
    • The questions were written from Wikipedia pages, so the score says how well pages are found and read, not how the models do on facts outside Wikipedia.
    • One index, one snapshot, one query rule, three introductions of 900 characters, one run at temperature zero.
    • The decision table cannot separate judgement from "always search" at this level of memory.
    • No fine-tuning. The group's method, reinforcement learning on tool calls, is the natural next step.
