What one Wikipedia lookup does to DAISY, and what it cannot do

DAISY, the group's quiz on the Danish Culture Canon, measures what a model remembers. Give the same models one lookup in Danish Wikipedia and the same quiz measures three separate skills: finding the page, reading it, and knowing when to look. With their prompt, their scorer and their questions, the group's own one-billion-parameter Mimir goes from to exact match, level with a model four times its size, because it reads Danish text better than anything else this small. No model here knows when to look: asked whether it knows the answer, Mimir says yes on of the questions it then gets wrong.

By Bolgaç Gülen, Odense, September 2026. Benchmark, prompt, scorer and model are the Odense NLP group's own (SDU-Daisy, DFM Mimir). Code, the index builder, every logged answer, and the task in the dfm-evals format: github.com/bolgacg/daisy-tools.

What you need to know to read this page

  1. DAISY is a quiz of short factual questions about the Danish Culture Canon, written by the group in Odense. 592 questions are public with their answers; those 592 are used here, and the group's own Mimir score was computed on the same 592.
  2. From memory means the model answers with nothing but the group's Danish prompt, at temperature zero, exactly as in their paper.
  3. One lookup means the question itself is sent to a search over Danish Wikipedia, and the introductions of the top three pages are placed above the question before the model answers. No model writes a query and nothing but the question is used.
  4. Two search engines are compared: Wikipedia's own search box, which needs every word of the query to appear in the page, and a standard ranked index (BM25) built here over the full Danish Wikipedia dump of 1 November 2023, which is older than the benchmark.
  5. Scores are the group's: exact match (the normalised answer equals the reference) and word-level F1. A contains-gold score is shown beside them: the reference appears somewhere inside the answer.
Answer recall@3
How often the reference answer is literally inside the three fetched introductions. This is the ceiling of a lookup: no model can score above it from the text alone.
Reading fidelity
Exact match on the questions where the answer was inside the fetched text. It separates "could not find it" from "could not read it".
Oracle query
The benchmark's hidden subject field, the name of the canon work, used as the search term. A model never sees it; it marks the best possible query.
Decision
Whether the model, told it may search, writes a search or answers from memory. The four counts of act three compare that choice with whether its memory was right.
Prefix attention
Mimir reads the prompt with every token seeing every other token, and only writes the answer left to right. The common laptop port reads the prompt left to right only, which is not how the model was trained.
Quantised
Weights stored at eight bits (six for Gemma) to fit a six-gigabyte consumer graphics card. Mimir itself runs in the official implementation at half precision.

Act two. One lookup, two search engines

Where the misses go

A lookup of three introductions therefore caps at ; whole pages would cap at . A labelled variant that adds the two best paragraphs of the same pages scores ; it is reported, not counted as the main line, because it is a second selection step.

Is the ranked index fair?

It uses the same source as the search box, the whole Danish Wikipedia, in a snapshot from 1 November 2023 that predates the benchmark. It is a generic BM25 index with the title weighted, built by a 60-line script in the repository, and the query is the question as written. No field of the benchmark other than the question is read. Anyone can rebuild it in twenty minutes.

With the page found and read, one skill remains, and it is the one the call names: does the model know when to look?

Act three. Does the model know when it does not know?

A model that searches on every question is a retrieval pipeline. One that never searches is a closed book. The useful behaviour is in between: look up what you do not know, answer what you do.

Why the score cannot yet test the decision

When a model is right from memory on 3 to 8 percent of questions, "always search" is close to the best policy, so a high rate of "searched when wrong" is not evidence of judgement. The decision problem exists for a model that knows a lot; the 70B model in the group's paper knew about a quarter. What can be measured now is the bluff: whether a model claims to know when it does not.

How this sits in the field

A number means little without the nearest published numbers beside it. Every mismatch is stated.

  • Same model, same shape of task, English. Search-R1 (arXiv 2503.09516) reports Qwen2.5-3B on PopQA at 10.8 percent direct, 38.7 with retrieval and 43.5 when trained to search, all contains-gold. Here, the same model on DAISY, contains-gold: direct, with one lookup on the ranked index, without any training. The Danish start is lower and the lookup lifts further, because the questions were written from Wikipedia pages.
  • English open-domain question answering. Systems trained for the task with far larger models score 44 to 64 exact match on Natural Questions (RAG 44.5, Fusion-in-Decoder 51.4, Atlas 64.0). An untrained 1B and 4B model at and here sit in that band; the tasks differ, so this is a placement, not a comparison.
  • Small readers fail to extract and get distracted. A 2026 study of retrieval utilisation (arXiv 2603.11513) finds sub-7B models lose known answers to distracting passages. Here the two best readers convert about 86 percent of fetched answers and the 1B Llama 45 percent, on identical text.
  • Adaptive retrieval pays only when memory is worth something. Mallen et al. (arXiv 2212.10511) retrieve on 40 percent of PopQA questions. Here memory is right on 1 to 8 percent, so always retrieving is the best policy, even though token log-probabilities predict correctness well (AUROC 0.83 to 0.91).
  • No published Danish retrieval-augmented QA number exists as far as the literature sweep found. The DAISY and Mimir papers report memory only. These tables are the first, which is a contribution and a reason for caution.

Model card and cost

ModelParametersWeights usedEM, one lookupSeconds per questionPrompt tokens per question

Nothing was trained. Five released instruction-tuned models were run as published. Four are quantised and served with llama.cpp; Mimir runs in the official implementation at half precision with prefix attention. Greedy decoding, at most 64 new tokens, the group's prompt, each model's chat template. The lookup is three introductions of at most 900 characters from the ranked index. Scores are the group's script, unmodified. Hardware: one GeForce GTX 1060 with six gigabytes of memory.

Baseline anyone could run without a model: the answer recall. A system that returned the fetched text verbatim would score zero on exact match but would contain the answer of the time. Reading fidelity measures how much of that the models convert.

Is it any good? As a measurement, yes: it reproduces the group's ranking on their own files and their Mimir number on their own code path. As a system, a one-billion-parameter Danish model with one lookup answers two thirds of this quiz exactly, from a card that costs less than a textbook.

Limits

  • 592 public questions. With 592, the 95 percent interval on a score near 65 is about plus or minus 4 points; differences of 3 points between two runs are noise.
  • The questions were written from Wikipedia pages, so once the right page is found the answer is almost always in it. The lookup result says how well pages are found and read, not how the models would do on facts outside Wikipedia.
  • One index, one snapshot (1 November 2023), one query rule (the question itself), three introductions of 900 characters. A sweep of the number of pages and the cut length is in the queue, not on this page.
  • One run per condition at temperature zero, one seed.
  • The decision table cannot separate judgement from "always search" at this level of memory, as act three states.
  • No fine-tuning. The group's method, reinforcement learning on tool calls, is the natural next step and was not attempted.

Run it yourself

The lookup is written as a task in the group's own evaluation library format (Inspect AI, as in dfm-evals), so it runs with the same command as their DAISY task against any OpenAI-compatible server.

pip install inspect-ai datasets
python scripts/build_localwiki.py          # the index, about 20 minutes, 0.9 GB
OPENAI_API_KEY=none inspect eval dfm_evals_task/daisy_lookup.py@daisy_lookup \
    --model openai/<served model> --model-base-url http://127.0.0.1:8080/v1

A second task, daisy_tool, offers the same search as a native tool call and lets the model decide. Both keep the upstream prompt, decoding and scorer.

How this was built

Their repository and dataset were pulled on 3 September 2026. A Python harness runs each condition against a local server and logs prompt, output, query, fetched titles, tokens and timing for every question. A second script scores every file with the group's metric code and writes the data behind this page. The runs took two nights on a second-hand desktop. All code, the logged rows and this page are in the repository linked at the top.
