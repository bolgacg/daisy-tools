Does a lookup tool close the gap for a one-billion-parameter Danish model?

Small open language models know almost none of the Danish Culture Canon: the group's own Mimir answers of the DAISY questions correctly from memory, and three multilingual models of one to four billion parameters do no better. Given one Danish Wikipedia lookup, every model improves by a factor of five or more, and the two models that can write their own search query reach . What none of them has is the judgement the call asks about: no model in this study knew when its memory was wrong, and the two that searched did so on nearly every question.

What you need to know to read this page

  1. DAISY is a quiz of 741 short factual questions about the Danish Culture Canon, written by the group in Odense; 592 of them are public with their answers, and those 592 are used here.
  2. A closed-book answer comes from the model's memory alone. Every model here was asked with the group's own Danish prompt, at temperature zero, exactly as in their paper.
  3. A lookup means the top three Danish Wikipedia article introductions for a search query are pasted above the question before the model answers.
  4. Agentic here means the model is told it may search, and decides on its own whether to write a search line or answer directly. That decision, not the score, is what the position's call names.
  5. Scores are the group's: exact match (the normalised answer equals the reference) and word-level F1. A lenient match is added beside them: the reference appears somewhere inside the answer.
Retrieval ceiling
How often the reference answer is literally inside the three retrieved introductions. No model can score above it from the text alone.
Shaped query
The question with its question words removed, shortened until Wikipedia's search returns something. A rule, not a model.
Oracle query
The benchmark's own subject field (the name of the canon work) used as the search term. Not available to a model; it marks the best case for asking.
Reading fidelity
Exact match on the questions where the answer was inside the retrieved text. Separates "could not find it" from "could not read it".
Quantised
Model weights stored at eight bits (six for Gemma) so they fit a six-gigabyte consumer graphics card. Small accuracy cost, stated in the model card.

The call, the benchmark and the group's own numbers

The scholarship call lists three directions: LLM customisation and test-time scaling, agentic behaviour and tool use, multi-modality and interactivity. This page is a small measured study on the second, with one line on the first. It uses the group's assets end to end so that the numbers can be read against their own tables.

Act one. How much of the canon do small models know?

This matters because everything after it depends on the starting point: a tool can only help a model that lacks the facts, and a model that answers from memory with confidence will not reach for one.

Click a model chip to highlight it; the bars show closed-book exact match for all five, the dotted line is the group's 70B result.

Small models hold almost none of this knowledge, and the Danish-trained one holds the most. Sampling five answers and voting, a minimal form of test-time scaling, changed no model by more than one point; there is nothing in memory to vote over.

Memory is thin across the board, so the next question is whether a single lookup can supply what memory lacks, and what limits it.

Act two. Does looking it up help, and what limits it?

What the tool cannot fix

With the best query available, the answer is in the fetched text for of questions; the rest are not in a Wikipedia introduction at all. And when the text does not contain the answer, every model still answers, almost always wrongly: exact match below 5 percent in that half for all five. None wrote "not found" more than a handful of times.

The tool works when the model asks well and reads faithfully. The remaining question, and the one the call asks, is whether a model knows when to ask.

Act three. Does the model know when it does not know?

This matters because an agent that searches on every question is a retrieval pipeline with extra steps, and one that never searches is a closed book. The useful behaviour is in between: look up what you do not know, answer what you do.

No model in this study made the decision the call describes.

Why this data cannot yet test the decision itself

When a model is right from memory on only 3 to 6 percent of questions, "always search" is close to the best possible policy, so a high rate of "searched when wrong" is not evidence of judgement. The real decision problem only exists for a model that knows a lot; the 70B model in the group's paper knew about a quarter. Testing that needs either a stronger model or a benchmark where small models know half. This page states the gap rather than claiming the result.

Nothing was trained. Five released instruction-tuned models were run as published, quantised to fit a GeForce GTX 1060 with six gigabytes of memory, served with llama.cpp (Mimir through the community pull request that adds its architecture), greedy decoding, at most 48 new tokens, the group's prompt and chat template of each model. Retrieval is the public Danish Wikipedia search and extract API, top three results, introductions cut at 900 characters. Scores are the group's script, run unmodified. The self-consistency row samples five answers at temperature 0.7 and votes.

Baseline anyone could run without a model: the retrieval ceilings. A system that returned the fetched text verbatim would score zero on exact match but would contain the answer of the time with the rule query and with the oracle query. Reading fidelity measures how much of that the models convert.

Is it any good? As a measurement, yes: it reproduces the group's ranking on their own files and Mimir lands within the expected range of their reported number given the subset and quantisation. As a system, the agentic Gemma and Qwen runs are a working Danish question answerer at 40 percent exact match on this quiz, from models that score 5 percent alone.

Limits

  • 592 public questions, not the 741 the papers report on; the public subset scores slightly higher for the same predictions.
  • Quantised weights (8-bit, 6-bit for Gemma) and a community implementation of Mimir's architecture; the paper's 9.6 was measured on full weights with the group's own harness. The gap to here is not explained on this page.
  • One retrieval source, one query rule, three snippets of 900 characters; no sweep of these was run.
  • One run per condition at temperature zero; no confidence intervals. With 592 questions, a difference of about 3 percentage points between two runs is within noise.
  • The decision-quality table cannot separate judgement from "always search" at this level of closed-book knowledge, as stated in act three.
  • No fine-tuning. The group's method, reinforcement learning on tool calls, is the natural next step and was not attempted.

How this was built

Their repository and dataset were pulled on 3 September 2026. A Python harness (about 400 lines) wraps the Wikipedia API with caching and rate limiting, formulates queries, runs each condition against a local llama.cpp server, and logs prompt, output, query, fetched titles and timing for every question. A second script scores every file with the group's metric code and writes the results page data. The runs took one night on a second-hand desktop with a GTX 1060. All code, the logged rows and this page are in the repository linked at the top.

Every number on this page is generated by the build script from the logged runs and the group's published files, as at . Sources: SDU-Daisy repository and dataset (MIT), the DAISY paper (arXiv 2601.19930), the DFM Mimir paper (arXiv 2608.13517), the Danish Wikipedia API.
