## 4. How they run Mimir in dfm-evals (and elsewhere)

### 4.1 The harness has no model code of its own

- dfm-evals is an Inspect AI extension package ("`dfm-evals` is a small extension package around `inspect_ai`", README line 3). Models are addressed by Inspect provider strings (`--model openai/...`, `vllm/...`); the CLI has no `hf` or transformers path (`dfm_evals/cli.py`; `grep -rn token_type_ids` over both dfm-evals trees returns nothing). Attention mode is therefore decided by whatever serves the model.
- The LUMI helpers serve models with `vllm serve` (e.g. `lumi/run_tournament.sbatch` line 763, `lumi/glm-4.7-smoke.sbatch` line 167) and talk to them through Inspect's `openai/` provider (`lumi/run_tournament.sbatch` line 834: `openai_model_ref` prepends `openai/`).

### 4.2 The serving paths in HRM-Text: both attend bidirectionally over the prompt

- The lab's eval scheduler (`schneiderkamplab/HRM-Text/eval_scheduler`) has two HRM server backends: `simple` (native) and `vllm`. `eval_scheduler/eval_scheduler/runtime.py` lines 810 to 811 define `use_vllm_hrm_server`, which returns true when the job is an external model or `job.metadata["hrm_server_backend"]` equals `"vllm"` (default `"simple"`). Line 857 to 861 starts `vllm.entrypoints.openai.api_server` for the vLLM path; `scripts/hrm_openai_server.py` wraps `evaluation.engines.SimpleEngine` (line 23, 231) for the native path.
- Native path: `models/layers.py` line 178 `is_causal = self.attn_type == "causal"`, and `_attention_with_cache` (lines 131 to 163) builds the SDPA mask as: `if causal: ... valid = valid[:, None, :] & (key_positions[None, None, :] <= query_positions[:, :, None]) else: valid = valid[:, None, :]`. With `attn_type = "prefixlm"` the prefill mask is only the key-validity mask, so every prompt token sees every other prompt token; decode steps are one query token attending to the whole cache. That is prefix-LM behaviour.
- vLLM path: vLLM's `vllm/model_executor/models/hrm_text.py` (added by `abcd1927` in vllm-project/vllm PR #43098, merged 2026-06-16) docstring lines 11 to 14: "The PrefixLM attention pattern (prompt bidirectional, response causal) is realized by reusing ``EncoderOnlyAttention`` (which sets ``causal=False`` unconditionally on every metadata build) but with ``attn_type=DECODER`` so the KV cache is allocated". Lines 206 to 211: "`PrefillPrefixLMAttention` forces `causal=False` on every metadata build, so the prompt attends bidirectionally during prefill (matching the HRM-Text training distribution), while `attn_type=DECODER` keeps the KV cache allocation needed by the recurrent forward. At single-token decode `causal=False` is a no-op." The PR body explains the unconditional choice: "Gating on `is_prefilling.all()` keeps `causal=True` in that mixed case, silently running the newly-prefilling requests as pure causal" and says that this "diverges from HRM-Text's PrefixLM training distribution".
- HRM-Text pins that vLLM: `pyproject.toml` `vllm==0.23.1rc1.dev102+ga46abb7ae` from `https://wheels.vllm.ai/a46abb7ae68acc13a4fc5870db98619b3f97c6e0/cu130`. The release evaluation of the shipped checkpoint used the vLLM path: `legal/registers/evaluation-register.csv` lists every dfm, euroeval and standard task for `step_1650000_ema` under `logs/dfm_evals/dfm8_XL_steps1250k_1450k_vllm_hrmenv/...` (plan `dfm8_XL_steps1250k_1450k_vllm_hrmenv_20260714_094255`), and the HF model card commit "Update model files to dfm8 XL step 1650000 ema" (2026-08-07) ties that checkpoint to the released weights.
- Transformers path: `huggingface/transformers` `src/transformers/models/hrm_text/modeling_hrm_text.py` (added by `abcd1927`, PR #46025, 2026-05-18; shipped in transformers 5.9.0 per the vLLM PR body) lines 449 to 451: "token_type_ids (`torch.LongTensor` of shape `(batch, seq_len)`, *optional*): Per-position bidirectional/causal indicator. Tokens with `token_type_ids == 1` form a single bidirectional block; all other positions are causal." Lines 478 to 484: `if token_type_ids is not None and is_first_iteration: if self.config.prefix_lm: mask_kwargs["block_sequence_ids"] = torch.where(token_type_ids == 1, 0, -1) ... attention_mask = create_causal_mask(**mask_kwargs)`. So without `token_type_ids`, plain `generate()` is causal. Lines 333 to 339 refuse FlashAttention when `prefix_lm` is true ("FlashAttention cannot represent the PrefixLM 4-D mask overlay. Use `'sdpa'` (default) or `'flex_attention'`"). This matches Bo's `scripts/mimir_official.py --prefix`, which passes `token_type_ids = torch.ones_like(ids)`.
- Conclusion for question 4: yes, the group's own harness attends bidirectionally over the prompt on both serving paths. The only causal-only runners in the wild are the community llama.cpp ports (sinimiini's patch, whose card says "Only the normal causal generation path is implemented in the patched runtime. Prefix-LM bidirectional `token_type_ids` are not supported by the `llama.cpp` path in this release", and noctrex's PR 27625, whose body says "causal attention only - the upstream prefix-LM mode is not implemented (the prefix_lm GGUF key round-trips unused)") and any transformers user who calls `generate()` without `token_type_ids` (Taylor-eOS/mimir `mimir.py` does exactly that; the two HF discussion threads by drkooler and Taylor-eOS also show plain `generate` usage).
- Quantised cards (schneiderkamplab/DFM-Mimir-FP8 and -AWQ-FP4, uploaded by JacobBITLABS 2026-09-03) state: "Evaluation settings: Temperature 0, shuffle seed 4242, full test datasets, HuggingFace Transformers inference (not vLLM), HRM builtin chat template." They report Daisy (EM) 8.8 for FP8 and 7.6 for AWQ FP4 against 9.6 for bf16 (FP8 card line 105, AWQ card line 109). Whether that transformers run passed `token_type_ids` is not stated. Speculation: 8.8 sits next to Bo's prefix number (8.4) and far from his causal number (5.4), which is consistent with prefix attention having been used, but the card does not say.
